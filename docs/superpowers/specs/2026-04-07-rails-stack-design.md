# Rails API stack — design

Add a Ruby on Rails (API-only) implementation of the Atlas Academy class scheduler API
alongside the existing TypeScript, Python, Java, and .NET stacks. The Rails app must
expose the same HTTP contract so the existing `web/` frontend works against it
unchanged.

## Goals

- Add `api/ruby/` containing a Rails 7+ API-only application that implements every
  endpoint listed in `README.md`.
- Add `docker-compose.ruby.yml` mirroring `docker-compose.python.yml`, so
  `docker compose -f docker-compose.ruby.yml up --build` brings up `api`, `db`, and
  `web`.
- Schema and seed data must be byte-equivalent (in effect) to the other stacks: same
  tables, columns, constraints, and the same 7 parents / 3 classes (Piano starts full
  at 2/2).
- Tests run via `cd api/ruby && bundle exec rspec` and exercise real database state
  (no mocking the DB), matching the project convention.
- Update `README.md` to document the new stack alongside the others.

## Non-goals

- No changes to the existing TypeScript / Python / Java / .NET stacks.
- No changes to the `web/` frontend.
- No new endpoints or business-logic differences.
- No production deployment concerns (Rails credentials, secret_key_base rotation,
  asset compilation, etc.) beyond what's needed to run locally and in Docker.

## Stack choices

| Concern        | Choice                                                              |
|----------------|---------------------------------------------------------------------|
| Framework      | Rails 7.x, API-only (`rails new --api`)                             |
| Ruby version   | 3.3 (matches `ruby:3.3-slim` Docker base)                           |
| ORM            | ActiveRecord (Rails default)                                        |
| Migrations     | ActiveRecord migrations, Ruby DSL (`db/migrate/*.rb`)               |
| Seeds          | `db/seeds.rb`, run via `rails db:seed` in Docker entrypoint         |
| Test framework | RSpec (`rspec-rails`), request specs in `spec/requests/`            |
| CORS           | `rack-cors`, allow all origins / methods / headers                  |
| Database       | PostgreSQL 16 via `pg` gem; `DATABASE_URL` env var                  |
| Server         | Puma (Rails default), bound to `0.0.0.0:4000`                       |

## Schema

One migration creates all three tables, identical in shape to the existing stacks:

- `parents(id uuid pk, email varchar(255) unique not null, name varchar(255) not null,
  created_at timestamptz default now())`
- `classes(id uuid pk, name varchar(255) not null, description text,
  capacity integer not null, start_time timestamptz not null,
  end_time timestamptz not null, created_at timestamptz default now())`
- `registrations(id uuid pk, class_id uuid fk → classes(id) on delete cascade,
  parent_id uuid fk → parents(id) on delete cascade,
  status varchar(20) not null default 'registered',
  created_at timestamptz default now(),
  unique (class_id, parent_id))`

UUIDs are generated by Postgres via `gen_random_uuid()` (built into PG13+, no
extension needed) — matching what the existing stacks do. The `id` column default is
set to `gen_random_uuid()` in the migration; ActiveRecord reads the generated id back
after insert.

The model for `classes` is named `Klass` (with `self.table_name = "classes"`) because
`Class` is a Ruby builtin.

## Seed data (`db/seeds.rb`)

- 7 parents with deterministic UUIDs (`11111111-...` through `77777777-...`):
  Alice Smith, Bob Jones, Carol Lee, Dan Patel, Eva Garcia, Frank Wu, Grace Kim.
- 3 classes with deterministic UUIDs (`aaaa...`, `bbbb...`, `cccc...`):
  - "Piano for Beginners" — capacity 2, starts in 7 days
  - "Chess Club" — capacity 3, starts in 14 days
  - "Art & Crafts" — capacity 4, starts in 21 days
- 2 registrations against Piano (Alice + Bob) so it starts full (2/2).

The seed file uses raw `ActiveRecord::Base.connection.execute` with the same
`INSERT ... ON CONFLICT (id) DO NOTHING` SQL the existing stacks use, so seeds are
idempotent and produce byte-identical state across stacks.

## Endpoints → controllers

| Method | Path                       | Controller#action       |
|--------|----------------------------|-------------------------|
| GET    | /health                    | `health#show`           |
| GET    | /classes                   | `classes#index`         |
| GET    | /classes/:id               | `classes#show`          |
| GET    | /parents                   | `parents#index`         |
| GET    | /registrations?parentId=   | `registrations#index`   |
| GET    | /registrations/all         | `registrations#all`     |
| POST   | /registrations             | `registrations#create`  |
| DELETE | /registrations/:id         | `registrations#destroy` |

### Response shape

Responses use **snake_case** keys to match the existing stacks and the frontend
contract. The POST request body is the only place camelCase appears: clients send
`{ "classId": "...", "parentId": "..." }`. Controllers build response hashes
explicitly — no serializer gems, no global key transform. Timestamps are ISO 8601
strings.

Per-endpoint shapes (matching `api/python/routes/`):

- `GET /classes` and `GET /classes/:id` →
  `{ id, name, description, capacity, start_time, end_time, created_at, registered_count }`.
  List ordered by `start_time ASC`.
- `GET /parents` →
  `[{ id, email, name }, ...]`, ordered by `name`.
- `GET /registrations?parentId=...` →
  `{ "registrations": [{ id, class_id, status, class_name }, ...] }`,
  filtered to `status = 'registered'`, ordered by class `start_time`.
- `GET /registrations/all` →
  `[{ id, class_id, class_name, parent_name, parent_email, created_at }, ...]`,
  filtered to `status = 'registered'`, ordered by class `start_time` then parent
  `name`.
- `POST /registrations` → 201 with body
  `{ "status": "registered", "message": "Successfully registered for class" }`.
- `DELETE /registrations/:id` → 204 no body.

### Error shape

Errors are rendered as `{ "error": "<message>" }` with the appropriate status code.
This matches the Python stack's `JSONResponse(status_code=..., content={"error": ...})`.
Implemented via a small `rescue_from` block in `ApplicationController`.

## Registration logic

`POST /registrations` is the only endpoint with non-trivial logic. The implementation
must mirror `api/python/routes/registrations.py::create_registration`:

1. Open a transaction and acquire a row-level lock on the class row
   (`Klass.lock.find_by(id: class_id)`, which issues `SELECT ... FOR UPDATE`). If the
   class is missing → `404 { "error": "Class not found" }`.
2. Look up the parent. If missing → `404 { "error": "Parent not found" }`.
3. Count active registrations (`status = 'registered'`) for that class. If
   `count >= capacity` → `409 { "error": "Class is full" }`.
4. **Upsert behavior**: if a registration already exists for `(class_id, parent_id)`,
   set its `status = 'registered'` (reactivating a prior cancellation). Otherwise,
   insert a new row with `status = 'registered'`.
5. Commit. Return `201 { "status": "registered", "message": "Successfully registered
   for class" }`. The created/updated row's id is intentionally not returned in the
   body — this matches the Python contract.

The `lock` + transaction prevents the TOCTOU race that the other stacks fix in commit
`c39ef9f`. Without it, two concurrent requests can both observe `count < capacity`
and both insert, exceeding capacity.

`DELETE /registrations/:id` is a **soft delete**: find the registration where
`id = :id AND status = 'registered'` (404 if missing), set `status = 'cancelled'`,
return `204` no body.

## CORS

`rack-cors` initializer:

```ruby
Rails.application.config.middleware.insert_before 0, Rack::Cors do
  allow do
    origins "*"
    resource "*", headers: :any, methods: %i[get post put patch delete options head]
  end
end
```

Matches the Python stack's permissive policy.

## Dockerfile

```dockerfile
FROM ruby:3.3-slim

RUN apt-get update -qq && \
    apt-get install -y --no-install-recommends build-essential libpq-dev && \
    rm -rf /var/lib/apt/lists/*

WORKDIR /app

COPY Gemfile Gemfile.lock ./
RUN bundle install

COPY . .

EXPOSE 4000

CMD ["sh", "-c", "bundle exec rails db:prepare && bundle exec rails db:seed && bundle exec rails server -b 0.0.0.0 -p 4000"]
```

`db:prepare` creates the DB if missing and runs pending migrations; it is idempotent
on restart. `db:seed` is idempotent because the seed file uses `find_or_create_by!`.

## Tests

RSpec request specs under `spec/requests/`, hitting the real test database. Each
example runs inside a transaction that is rolled back at the end (Rails' default
`use_transactional_fixtures = true`), so no `DatabaseCleaner` gem is needed.

Mirrors `api/python/tests/`:

- `health_spec.rb` — `GET /health` → 200, body `{ "status": "ok" }`
- `parents_spec.rb` — `GET /parents` returns the 7 seeded parents
- `classes_spec.rb` — `GET /classes` returns all classes with `spotsAvailable`
  computed correctly; `GET /classes/:id` returns 404 for an unknown id
- `registrations_spec.rb`:
  - happy path: register a parent for a non-full class → 201
  - duplicate registration → 409
  - registering for the full Piano class → 409
  - registering with an unknown class id → 404
  - registering with an unknown parent id → 404
  - `GET /registrations?parentId=...` returns only that parent's registrations
  - `GET /registrations/all` returns every registration
  - `DELETE /registrations/:id` soft-deletes (status='cancelled') → 204; second
    delete on the same id → 404 (because the WHERE filters on `status = 'registered'`)
  - registering a parent who has a cancelled registration for that class
    reactivates it (upsert behavior) → 201, single row in the DB with status
    `'registered'`

The seed data is loaded into the test DB before the suite runs (via a `before(:suite)`
hook in `rails_helper.rb` that runs `Rails.application.load_seed`), so each spec
starts from the same fixture state as the other stacks' tests.

## Risks and open questions

- **Rails boot time in Docker**: Rails has a noticeably slower cold start than the
  FastAPI app. The `web` service's `depends_on: api` will not block on the API being
  ready (only on the container being created), so the first frontend request after
  `up` may briefly 502. This matches existing stacks' behavior — no fix needed.
- **UUID generation**: `gen_random_uuid()` is built into PostgreSQL 13+ (no extension
  required). The migration sets it as the column default; ActiveRecord will read the
  generated id back after `INSERT ... RETURNING id`.
- **`Klass` model name**: Anyone reading the code needs to know `Klass` maps to the
  `classes` table. A comment on the class declaration handles this.
